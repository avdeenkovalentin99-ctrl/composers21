# Архитектура сайта Композиторы XXI века

Проверка 28 октября 2026 года. Только аудит; исходники не изменялись. Временное hero-видео и принятое расположение cookie notice не входят в задачи исправления этого раздела.

## Оценка основы

React, TypeScript strict, Vite, маршруты с lazy loading и статическая публикация — пригодная основа для этого сайта. Выбор стека не устарел. Переход на Next.js, добавление backend, Redux или CMS только ради современности не обоснованы.

Основной долг находится в границах ответственности: итоговые данные объединяются в браузере; персональная страница получает весь сборник биографий; переходы и scroll lock имеют несколько владельцев; накопленные браузерные проверки не входят в выпуск. Исправлять стоит эти конкретные места, сохраняя работающие решения.

Что уже сделано правильно:

- `tsconfig.app.json:13–16`: strict, проверки неиспользуемых сущностей и fallthrough. `package.json:12`: build включает TypeScript.
- `router.tsx:16–31`: страницы действительно разделены lazy import. Главная в проведенном замере загрузила **17 собственных JS-запросов, 178 137 байт transfer** с HTTP overhead. Биографии и все остальные страницы в эту загрузку не вошли.
- `layout/viewportFrame.ts:1–40`: общий passive scroll listener, разделение чтений геометрии и DOM-записей. Это осознанная оптимизация.
- В анимационных hooks уже есть reduced motion, очистка подписок и видимость. `useMediaSyncopation.ts` также завершает эффект при ошибке и возвращает видимость при focus. Называть все effects бесконтрольными было бы неверно.
- Desktop/mobile меню используют общий `data/navigation.ts`; выбранная трансляция на главной имеет общий state.
- Глобальный CSS — **586 строк и 15 836 байт исходника**. Размер сам по себе не требует смены CSS-подхода.

## Десять решений

P1 — надежность пользовательского сценария; P2 — плановое техническое улучшение. Стоимость указана относительно объема изменений, без предположительных сроков.

### 1. P1 Единый жизненный цикл перехода и прокрутки

**Доказательство:** `src/app/router.tsx:161–180` фиксирует body и переписывает шесть inline свойств; `184–185` отключает browser scroll restoration; `235–240` разблокирует страницу и обнуляет позицию при завершении exit; `254–262` связывает lazy outlet с `AnimatePresence mode="wait"`. Отдельно `SiteHeader.tsx:228–234` и `MobileNavigation.tsx:40–45` меняют overflow documentElement.

**Цена:** нет отдельной политики восстановления позиции на Back; правильность навигации связана с завершением оформления. Несколько владельцев блокировки повышают риск ошибки при быстрой смене маршрутов, resize и закрытии меню. Дедлок только по коду не считается воспроизведенным.

**Минимальное решение:** один hook/сервис scroll lock, сохраняющий прежние значения; явная политика PUSH/POP/hash; восстановление позиции на Back, начало страницы на новой навигации. Exit-анимация не должна быть единственным способом снять блокировку; учесть reduced motion. Стоимость средняя, замена роутера не нужна.

### 2. P1 Обработка ошибок lazy routes

**Доказательство:** `router.tsx:145–146,262,271–299` использует визуально пустой suspense fallback, собственного errorElement/ErrorBoundary нет. У React Router есть стандартная обработка, но пользовательский сценарий восстановления проектом не задан.

**Цена:** потеря сети или удаленный старый chunk могут привести к пустому ожиданию/стандартному экрану ошибки без понятного действия.

**Минимальное решение:** общий экран ошибки с повтором и полной перезагрузкой, доступный статус загрузки. Для ошибки версии chunk допустима одна контролируемая перезагрузка, без циклов. Проверка — offline-переход на ранее не открытую страницу. Стоимость малая/средняя.

### 3. P2 Подготовка итогового контента при сборке

**Доказательство:** `data/composers.ts:1–36` и `data/performers.ts:1–36` содержат одинаковый runtime merge legacy/generated. `data/personDetails.ts:1–10` также объединяет legacy и generated. `scripts/build-bios.ts:1` отключает проверку типов через ts-nocheck, `216–217` записывает generated outputs. Обычный build не проверяет их актуальность относительно исходного Markdown.

**Цена:** редактирование требует знания приоритета нескольких версий данных. Можно успешно собрать устаревшие generated-файлы. Часть обработки контента повторяется в браузере.

**Минимальное решение:** зафиксировать существующие приоритеты, перенести объединение в build, получать один нормализованный dataset. Валидировать unique slug, обязательные поля, ссылки на фотографии и связность концертов. В CI сверять воспроизводимость generated outputs. tmp_data содержит настоящие исходники и не является мусором; перенос в content возможен только с обновлением всех путей. Стоимость средняя. CMS пока необязательна.

### 4. P2 Более точные границы данных при сохранении lazy loading

**Измерено:** `biography-*.js` — **347 793 байта raw / 86 038 gzip**. Его импортируют `ComposerPage.tsx:4`, `SoloistPage.tsx:4`, `EnsemblePage.tsx:4`; `data/biography.ts:1` тянет весь personDetails. На главной этот chunk отсутствует. На главную приходят broadcasts и полный concertProgrammes (`broadcasts.ts:1,538`; `FestivalPageLegacy.tsx:13,24–38`), хотя превью используют малую часть полей.

**Цена:** для одного участника скачиваются все биографии; главная связана с подробной программой концертов. Это лишняя связность и трафик, а не «весь сайт в одном bundle».

**Минимальное решение:** генерировать compact previews/cards отдельно от details. Для биографий выбрать группировку по типу или статические страницы; не создавать сотню микрочанков автоматически. Сохранять рабочий route-level split. Стоимость малая для preview и средняя для details.

### 5. P2 Подготовка шрифтов и изображений как часть сборки

**Доказательство:** `globals.css:10–32` подключает три полноразмерных TTF. В обоих сетевых профилях шрифты передали **2 213 118 байт**, примерно **12,4×** больше собственного initial JS. `data/images.ts:5–8` eager-glob включает URL фотографий в сборку; это не означает скачивание всех фото браузером. На mobile пришел `p31.png` 566 234 байта: desktop img в скрытой секции `FestivalPageLegacy.tsx:139,165` не имеет lazy, mobile img имеет (`MobileHomeBroadcasts.tsx:27`).

**Цена:** оптимизация React сама по себе не устранит основной постоянный ресурсный расход. CSS display:none не контролирует сетевые запросы img.

**Минимальное решение:** сохранить гарнитуры, подготовить WOFF2 и нужные языковые subset, проверить fallback metrics. Генерировать варианты размеров фотографий и manifest с width/height/srcset. Согласовать lazy у скрытого представления трансляций. Стоимость средняя с измеримой отдачей. Временное видео здесь не оценивается.

### 6. P2 Общий контракт адаптивных представлений

**Доказательство:** `FestivalPageLegacy.tsx:135–139,235,330` одновременно монтирует mobile/desktop секции и скрывает их CSS. Для разных художественных композиций это допустимо. Условие desktop повторяется в `homeViewport.ts:1–2` и `globals.css:3–7`; `HomePhoneLandscape.css:1–88` дополнительно переопределяет дочерние компоненты. Пункты года повторяются в `MobileFestivalYear.tsx:6–12` и desktop JSX.

**Цена:** изменение пункта, DOM или breakpoint требует синхронизации нескольких мест; скрытая ветка остается смонтированной. Это не доказанная проблема screen reader: display:none скрывает ветку от accessibility tree.

**Минимальное решение:** общие данные year navigation и state; размеры/gutters через локальные tokens; отдельный markup оставить только для действительно разных композиций. Проверять соответствие JS/CSS breakpoint и пограничные размеры. Не заменять все условным mount через window.innerWidth: он может сбрасывать состояние при повороте и усложнит prerender. Стоимость малая/средняя; полный переход на CSS Modules/CSS-in-JS не нужен.

### 7. P2 Ограничить ответственность авторских анимаций

**Доказательство:** hooks `useMediaSyncopation` 418 строк, `useFestivalFigureMotion` 206, `useFestivalYearEntrance` 111, `useBroadcastEntrance` 90 выполняют разные задачи, не являясь полными дубликатами. Общий scheduler уже есть. Готовность секции года зависит от animationend/opacity (`useFestivalYearEntrance.ts:68–80`); media hook связан с data-атрибутами DOM и played memory (`useMediaSyncopation.ts:31–45,291–336`).

**Цена:** изменение CSS/разметки может нарушить readiness без ошибки TypeScript. Само число строк не доказывает низкую скорость; attribution long tasks требует profiling.

**Минимальное решение:** для каждой секции определить pending/running/complete, отмену и fallback «контент доступен». Проверять focus, resize, reduced motion, unmount общей матрицей сценариев. Держать визуальные timing/config отдельно от lifecycle; развивать существующий scheduler при необходимости. Не менять Motion на другую библиотеку без измерений. Стоимость средняя, отдача в устойчивости доработок.

### 8. P2 Поэтапная HTML-публикация контентных страниц

**Доказательство:** `index.html:33–36` содержит пустой root, `main.tsx:7` — createRoot. Metadata меняются после JS (`router.tsx:194–196`, `pageMeta.ts:37–75`). Основное содержимое — редко меняющиеся биографии, программы и информация, а не персональные данные пользователя.

**Цена:** первый содержательный экран зависит от JS; роботы получают общий исходный HTML. CSR не равно отсутствие индексации — Google исполняет JavaScript, но рендеринг остается дополнительной зависимостью.

**Минимальное решение:** сначала исправить уникальность metadata/canonical в текущей модели. Затем отдельным этапом проверить build-time prerender/SSG публичных маршрутов с HTML, уникальным head и правильными status/redirect на хостинге. React/Vite можно сохранить; SSR-сервер оправдан лишь при данных, требующих ответа на каждый запрос. Проверить browser-only effects и hydration. Стоимость поэтапная; не откладывать текущие баги ради миграции. [Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

### 9. P2 Атомарный выпуск и сохранение предыдущей версии

**Доказательство:** `.github/workflows/deploy.yml:4–6,22–37` на push main копирует dist прямо в TARGET через rsync с --delete. В workflow нет concurrency, smoke check после выпуска и переключения подготовленного release. Third-party `easingthemes/ssh-deploy@main` не закреплен на неизменяемом SHA.

**Цена конструкции:** возможна смесь HTML/chunks разных версий во время копирования. Уже открытая вкладка может запросить удаленный старый lazy chunk. Два выпуска могут пересечься. Это риски механизма; инциденты production здесь не воспроизводились.

**Минимальное решение:** новый release-dir → проверка → атомарное переключение; хранение предыдущего релиза и старых файлов для открытых вкладок; последовательность deploy через concurrency. Закрепить action SHA. Если release-dir невозможен, минимум — assets прежде HTML и отложенное удаление старого набора. Стоимость средняя, зависит от хостинга; его фактическая конфигурация не подтверждена.

### 10. P2 Небольшой постоянный выпускной контроль

**Доказательство:** `package.json:5–13` не задает test/lint; `.github/workflows/deploy.yml:22–25` выполняет npm ci/build. Есть `scripts/media-syncopation.test.mjs`, но он не включен в workflow. Многие браузерные проверки находятся в игнорируемой .tmp-audit и не воспроизводятся из чистого checkout. TypeScript strict уже есть, поэтому говорить об отсутствии проверок вообще неверно.

**Цена:** клавиатура меню, Back, hidden resources, slug и переносы могут сломаться при зеленой сборке. Чистка temp-dir удаляет накопленные сценарии проверки.

**Минимальное решение:** сохранить небольшой smoke suite в tests: меню/подменю, Tab/Escape, прямой вход и Back, карточка каждого типа, pageerror/внутренние URL, portrait/landscape/reduced motion. Проверять production build, данные и ресурсные budgets в CI. Screenshot comparisons оставить ключевым экранам; не превращать каждый отступ в unit test. Стоимость средняя.

## Целевая структура без лишних подсистем

```text
content sources → build normalization and validation → route datasets + asset manifest
                                                               ↓
pages → shared layout/navigation → sections → scoped styles and animation config
  ↓               ↓
route metadata    scroll/focus lifecycle
  ↓
production build → type/data/browser checks → versioned release → smoke check
```

Глобальный store, API и CMS добавлять по реальной потребности. Не заменять все imports сетевым fetch ради абстрактного разделения: это может добавить задержки на простом статическом сайте. Не склеивать все chunks: lazy split работает. Не удалять legacy-файлы по названию — текущая главная сама FestivalPageLegacy, legacy-data участвуют в рабочих объединениях.

Измерения: `architecture-metrics.json` содержит размеры/импорты chunks и сводку запросов из `performance-results.json`. Локальные значения не описывают 75-й перцентиль реальных посетителей и не доказывают прохождение Core Web Vitals.
