## Архитектура и техническая правильность

### Что уже сделано разумно

- Страницы подключаются через `lazy`, есть `Suspense`. Биографии не входят в начальную загрузку главной. Утверждение «весь сайт загружается одним огромным bundle» здесь неверно.
- Данные в основном отделены от JSX; у сущностей есть slug и типы.
- Включены строгие проверки TypeScript, неиспользуемых переменных и параметров.
- Для многих изображений есть `loading="lazy"`, `decoding="async"` и зарезервированные пропорции.
- У мобильного меню уже реализованы начальный фокус, удержание Tab, Escape, возврат фокуса и `inert` закрытых панелей.
- `viewportFrame.ts` объединяет работу с прокруткой через `requestAnimationFrame`; scroll listener пассивный. Это полезная координация, которую стоит сохранять.
- В ряде анимаций есть reduced-motion; медиаресурсы при уходе из области просмотра/вкладки приостанавливаются.
- Есть `robots.txt`, sitemap, canonical, Open Graph и автоматическая сборка в CI. Дорабатывать нужно их согласованность, а не создавать все с нуля.

### А1 Один владелец метаданных

**Приоритет P1. Ошибка воспроизведена.** `RootLayout` применяет метаданные маршрута, но `AcademiesPage` дополнительно меняет `document.title` и description и восстанавливает старые значения при размонтировании. Из-за отложенного удаления страницы анимацией cleanup срабатывает уже после назначения метаданных нового URL.

Сценарий: прямой вход `/academies` → «Медиа» → дождаться перехода. Адрес `/media`, заголовок вкладки «Академии», description от Академий. Это архитектурный конфликт двух владельцев состояния, а не случайная опечатка.

**Решение:** один механизм метаданных, получающий маршрут и данные сущности. Страницы не восстанавливают старую мету в cleanup. ### А2 Общие правила для меню и модальных окон

**Приоритет P1. Два разных дефекта воспроизведены.** Мобильное меню, desktop drawer и окно Академий реализуют управление фокусом независимо. В одном месте есть полноценная обработка клавиатуры, в двух других она неполная.

### А3 Одно правило истории и прокрутки

### А4 Канонический источник контента и проверяемая генерация

**Приоритет P1. Это наиболее существенный дефект качества данных.** Текущий путь данных:

```text
tmp_data/*.md
    → scripts/build-bios.ts
    → participants.generated.ts и personDetails.ts
    → объединение с *.legacy.ts
    → composers / performers / participants
    → каталог и персональные страницы
```

Само наличие генерации нормально. Неправильно, что конфликтующие записи тихо разрешаются по разным правилам: список берет последнюю запись с данным slug, биографии выбираются по длине. Поэтому дубли скрываются, но неоднозначность остается. `mergeBySlug` почти одинаково написан в двух файлах; генератор использует `@ts-nocheck`.

Подтверждены последствия:

- Один абзац «Многогранный музыкант, проявляющий себя в трёх основных сферах: фортепиано, композиция, педагогика» повторяется в **38 разных биографиях**. У Марианны Домниковой и Михаила Тарбагаева это единственный абзац. В исходных материалах эта фраза также является описанием Ольги Ивановой. История Git связывает массовое появление с добавлением импорта 18 апреля; подробнее ниже.
- В биографии Леонида Десятникова отдельно повторены произведения, уже перечисленные выше. Это видно на [снимке страницы](screens/detail-composers-1440.png).
- `artem-makoyan` дважды находится в generated-массиве с разными описаниями; `Map` скрывает дубль в интерфейсе.
- Для шести ансамблей внешний URL из generated-данных перекрывает уже имеющееся локальное фото.
- У Максима Новикова отсутствует полная biography-запись; выводится предусмотренное краткое описание на 135 символов.

**Решение:** определить авторитетный источник каждой записи; исправить исходные Markdown-данные и только потом перегенерировать. На этапе генерации проверять уникальность slug, обязательные поля, существование локальных изображений и ссылок, конфликт версий и подозрительно одинаковые абзацы. Ошибка импорта должна останавливать генерацию с понятным сообщением, а не молча выбирать «более длинный» вариант. Базу данных или CMS вводить только при реальной необходимости редакторской работы нескольких людей.

### А5 Анимация не должна определять доступность содержания

**Приоритет P2.** На главной ссылки блока «2026» начинают появляться только через 4,45 секунды после запуска анимации. Последняя заканчивает появление примерно через 6,55 секунды. До этого область выглядит пустой — часть впечатления «слишком большой отступ» объясняется именно скрытым содержимым.

В браузерной проверке ссылка получила фокус, оставаясь с `opacity: 0`. Это уже функциональная проблема: пользователь клавиатуры может попасть на невидимую навигацию. Reduced-motion предусмотрен для этого блока, но обычный режим тоже должен сохранять видимый фокус.

Общие переходы страниц, blur списка, задержки текста биографий и smooth scroll не используют единое правило reduced-motion. CSS и JS обрабатывают настройку раздельно.

**Решение:** важные ссылки и текст доступны сразу; декоративные элементы могут анимироваться отдельно. При focus анимация немедленно завершается. Установить общие правила длительности, reduced-motion и поведения при повторном входе. Не заменять существующий `viewportFrame` множеством новых scroll handlers.

Код: `FestivalYearEntrance.css:41`, `:54`; `useFestivalYearEntrance.ts`; `router.tsx:256`; `globals.css:47`; `AfishaPage.tsx:365`. Доказательство: [interaction-results.json](evidence/interaction-results.json).

### А7 Доставка публичного контента и индексирование

**Приоритет P2, после исправления данных и поведения.** Сейчас это клиентская SPA: исходный HTML содержит пустой `#root`, общие метаданные и canonical главной. JavaScript создает содержание и уточняет canonical. Даже после выполнения JS Open Graph и Twitter title/description берутся из общих констант.

Для преимущественно статического фестивального архива полезен **предварительный рендер HTML при сборке** основных разделов и профилей: содержимое, персональная мета и ссылки доступны до запуска JS. Это обоснованный следующий шаг для поиска, шаринга и устойчивости загрузки. Обязательной миграции на Next.js, постоянного SSR-сервера или нового backend из этого не следует. Сначала стабилизировать данные и URL, затем выбрать простейший способ статической генерации под существующий хостинг.

Дополнительные несогласованности:

- В sitemap есть 10 основных URL и 15 `?concert=...`, но canonical всех концертных вариантов указывает на `/afisha`. Выбрать модель: отдельные индексируемые страницы концертов либо одна страница и query только как состояние интерфейса. Во втором случае не представлять query-варианты как самостоятельные канонические страницы в sitemap.
- В sitemap нет 86 профилей; это особенно нежелательно вместе с button-навигацией. Генерировать карту из реального каталога.
- Локальный preview возвращает HTTP 200 для несуществующего пути, затем клиент рисует «Страница не найдена» и `noindex`. Несуществующий профиль перенаправляется в каталог. Серверную обработку 404 на production нужно проверить отдельно; локальный статус нельзя приписывать серверу.

Google обрабатывает JavaScript, поэтому утверждение «SPA совсем не индексируется» было бы неверным. Рекомендация касается надежной доставки содержания, ссылок и метаданных. Основание: [Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

### А8 Обработка ошибок и выпуск новой версии

**Приоритет P2. Риски по коду, не авария production.** Для lazy routes есть пустой loading fallback, но нет собственного понятного error/retry интерфейса. Чтение localStorage/sessionStorage не защищено от исключений. CI собирает проект и сразу публикует `dist` через rsync с `--delete`.

При новой публикации старые hash-чанки могут исчезнуть, пока пользователь еще держит открытую предыдущую версию приложения. При последующем переходе lazy import может не загрузиться. Это известный сценарий для такой схемы, но на публичном сервере он здесь не воспроизводился.

**Решение:** граница ошибок маршрута с понятным восстановлением; безопасный адаптер browser storage; атомарная публикация с сохранением доступности прежних hash-чанков либо версионированных путей; предсказуемые заголовки кеширования. Само переключение каталога без доступности прежних ресурсов не спасает уже открытые вкладки. Добавить в CI проверки критичных сценариев: меню, modal, метаданные после перехода, Back, 320 px, битые локальные ссылки и качество данных. Существующие семь тестов проверяют только отдельную анимационную логику и не запускаются текущим deploy workflow.

Зависимость `easingthemes/ssh-deploy@main` закреплена на плавающей ветке. Для воспроизводимой публикации закрепить проверенный commit и определить политику обновления; предусмотреть порядок параллельных релизов и возможность отката.

Код: `router.tsx:146`, `:262`; `ParticipantsPage.tsx:200`; `FestivalPageLegacy.tsx:58`; `.github/workflows/deploy.yml:23`; `package.json:6`.

### А9 Сократить действующую поверхность проекта

**Приоритет P2 для public, P3 для организации исходников.** Статический граф нашел 24 файла исходников, недостижимых от `main.tsx`. ### А10 Уточнить границы данных и адаптивных представлений

**Приоритет P2, постепенная доработка.** Для одного профиля сейчас загружается весь сборник биографий. На главной вместе с превью трансляций подключается полная программа концертов через `broadcasts.ts`. При нормализации данных стоит отдельно генерировать короткие сведения для карточек и подробное содержание. Делить все на десятки мелких запросов без замера не требуется: текущий chunk биографий около 86 KB gzip, и он кешируется между профилями.

Mobile/desktop секции главной одновременно монтируются и скрываются CSS. Для разных графических композиций это допустимо, но данные, выбор активной трансляции и правила breakpoint должны оставаться общими. Часть этого уже реализована; список навигации года и условие desktop дублируются. Нужно устранить расхождение источников, сохранив отдельную разметку там, где она действительно нужна. `display:none` скрывает ветку от чтения экранным диктором, но само по себе не гарантирует отсутствие сетевого запроса изображения.

Код: `biography.ts:1`; `broadcasts.ts:1`; `FestivalPageLegacy.tsx:13`, `:139`; `MobileFestivalYear.tsx:6`; `homeViewport.ts:2`; `globals.css:3`. Подробная техническая схема и дополнительные измерения: [architecture-notes.md](architecture-notes.md).

Нет оснований вводить микросервисы, новую базу данных, Redux, сложную универсальную дизайн-систему или менять фреймворк исключительно ради слова «современный». Нужна меньшая неоднозначность в существующем проекте и проверки именно тех сценариев, которые уже дают сбои.
